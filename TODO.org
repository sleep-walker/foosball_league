 OK, I'm a bit skeptical about the proposed API. Let's start over. I'd like to create API for foosball league, which is easy to use by frontends.

 - User
    - those who access foosball league application itself
    - registration can be manualy verified or open
    - some Users can be organizers of league or tournaments or game - they can also delegate administration (or transfer ownership)
    - there should be administrators of the system so the app can be effectively maintained without knowledge of the system internals.

- Player
    - participants of the foosball games itself
    - they can be registered users or not

- Game
    - a game is played by two players (or teams)
    - it has a result
    - it can be part of a tournament stage, tournament or league

- Tournament
    - a collection of games or stages

- Tournament stage
    - tournament can have play off and group stages

- League
    - a collection of tournaments
    - they have common rules

- Rules
    - rules used for league or tournament or tournament stage

- API
    - should be easy to use by frontend applications
    - should be easy to use by other applications (e.g. for statistics)
    - should be easy to use by mobile applications
    - should be easy to use by CLI applications
    - exposed information are Players, Games, Tournaments, Tournament Stages, Leagues, Rules

* API Resource Structure (RESTful)
** Users
Users of the application. Those are the ones who can observe
tournaments and leagues or even organize those. There is also
superuser - administrator. A user, who is responsible for the
deployment of the application.

If the instance is open, users can register themselves. If not, users
can be registered by administrator.

Only verified users can act because e-mail address is used as an
identificator and verification of the control is a way to ensure
uniqness.

- [X] register
  POST /api/v1/users/register

- [X] login
  POST /api/v1/users/login

- [X] logout
  POST /api/v1/users/logout

- [ ] REST users
  GET /api/v1/users/{user_id} — Get user by ID
  PATCH /api/v1/users/{user_id} — Update user (admin only)
  DELETE /api/v1/users/{user_id} — Delete user (admin only)

- [X] self-management
  GET /api/v1/users/me — Current user profile
  PATCH /api/v1/users/me — Update current user profile
