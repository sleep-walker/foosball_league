*** [X] Score erosion for league standings — service layer
    =LeagueService._placement_standings= is complete (commit 5f0f886).
    It iterates over the finished tournaments ordered by
    =Tournament.date= (oldest first → erosion decay); for each
    tournament it takes the finished stage with the highest =ordering=
    as the "final" one, calls
    =TournamentService.get_stage_standings= and converts the result into

** Perf debt 🐌
*** [ ] Eager-loading audit (=lazy="selectin"=)
    31 relationships across the models use =lazy="selectin"= as default,
    which forces an extra SELECT for the relation on every access — even
    for endpoints that don't touch it (e.g. =GET /leagues= loads each
    league's tournaments, seasons, rule_presets, members; each tournament
    then expands its stages, matches, teams, registrations, applicants,
    co-organizers → exponential fan-out).

    Plan:
    1. Add SQL counting fixture (=event.listens_for(Engine, "before_cursor_execute")=
       in conftest) and assert sane query counts on key endpoints
       (=GET /leagues=, =GET /tournaments=, =GET /tournaments/{id}=).
    2. Switch problematic relations to =lazy="raise"= (or unset).
    3. Add =selectinload(...)= to the few CRUD/repository queries that
       actually need the relation.
    4. Repeat per-domain — Players is already lean, start with Leagues.

    Currently safe: =get_tournament= in tournaments/crud.py already does
    explicit =subqueryload= chains, so the selectin defaults are
    redundant duplicate work there.

*** [ ] Multi-worker WebSocket fan-out
    The current WS implementation uses an in-process broadcast — it only
    works with a single worker process. For a multi-worker deployment:
    - Option A: PostgreSQL LISTEN/NOTIFY (no extra dependency,
      Postgres alone is enough, native pub/sub)
    - Option B: Redis pub/sub (faster, but an extra service)
    Postgres LISTEN/NOTIFY is preferred — it needs no additional infra.

*** [ ] Fixed teams (named doubles)

    round, per-player standings).  Fixed teams = a different player_mode.
    - Team entity: team name + player 1 + player 2
    - When adding to a tournament: add teams instead of individuals
      (either pick an existing one or create a new one)
    - Look up an existing team by its combination of players (A+B = B+A)
    - Per-team standings (participant_id = team UUID, nickname = team name)
    - No decomposition into individuals (unlike DYP)
    - player_mode: "singles" | "dyp" | "fixed_doubles"
    - UI: team registration form (name, 2× player autocomplete)
